# Ask Cova: server rollout gate

**Implementation is disabled by default. This document is not deployment, spending, credential-provisioning, or database-change authorization.** No paid calls, customer-data calls, credential reads, external configuration changes, or deployment were used for these regressions.

## Boundary and contract

Ask Cova uses POST actions on the existing `/api/workspace`, not a new function. The existing workspace-enabled/project-binding guard, policy-accepted authentication, UUID validation and exact owner comparison run before discovery or dispatch. A bounded routing-body parse selects authentication options; parse errors are deferred until after authentication. Only `ask_cova` and `ask_cova_access` POST actions call `requirePolicyAcceptedUser(req, {billing:false})`: verified Supabase identity and current-policy acceptance remain mandatory, without subscription resolution. Existing consent/apply/GET retain the original default billing authentication, including billing-derived workspace trade limits. Free and Pro use identical conservative Ask Cova limits; this adds no subscription gate.

### Single-account private beta

`server/askCovaAccess.ts` exports the shared `hasAskCovaAccess` gate used by both the workspace dispatcher and the actual Ask Cova handler. Access requires **both** literal server `ASK_COVA_ENABLED=true` and one valid, exactly 36-character UUID in server-only `ASK_COVA_BETA_USER_ID`, exactly matching the policy-verified authenticated `user.id`. There is no default, broad-enable fallback, list, wildcard, email rule, metadata rule or frontend configuration authority. Whitespace is not trimmed and identity is not guessed or normalized. The real approved account UUID must be independently verified and configured by a separately authorized operator; no account identity is hardcoded here. All regression account IDs are synthetic.

Missing/malformed configuration, a nonmember, or the kill switch returns generic HTTP 404 `{status:'unavailable',error:'ask_cova_unavailable'}` for `ask_cova`. Neither the configured UUID nor an invitation reason is disclosed. Authorization precedes workspace snapshot reads, budget configuration/reservation, Redis and provider calls, even when the actual handler is called directly. Direct handler callers must supply the already-verified auth user, never a user derived from request fields. The route retains `requirePolicyAcceptedUser` (Supabase `/auth/v1/user` verification plus current-policy acceptance), explicitly with `billing:false` for the two Ask Cova POST actions so even separately configured billing cannot contact billing Redis or Stripe before denial/discovery; no JWT body decoding or email-to-UUID guessing is introduced.

Capability discovery is **POST** `/api/workspace` with exactly `{action:'ask_cova_access',owner}`. After the existing project/auth/policy/same-owner checks, it returns exactly `{owner:user.id,enabled:boolean}` with `Cache-Control: private, no-store`. Nonmembers receive `enabled:false` for their own authenticated owner, never the invited identity. Extra fields and raw duplicate JSON properties are rejected. Discovery does not read a trading snapshot, check provider credentials, reserve budget, contact Redis, or dispatch a provider call. `enabled:true` means beta authorization only, not provider/budget readiness or spending permission. Pre-parsed bodies cannot reveal duplicates already discarded by the hosting platform. GET remains workspace snapshot loading, not a discovery alias. Existing GET/apply/consent remain available to nonmembers under their unchanged checks.

The request has exactly `action`, `owner`, `account`, `range`, `question`, `contextDigest`, `protocolVersion`, and UUID `requestId`. Protocol must be exactly `ask-cova-v2`; the UTF-8 serialized request is limited to 4 KiB (including whitespace when raw text is available). Client trades, notes, metrics, arbitrary questions and provider configuration are not accepted. Duplicate properties are rejected when raw request text is available; when the hosting platform supplies a pre-parsed object, overwritten JSON properties are no longer observable. The surviving object still undergoes the exact field/value checks.

Server reads are owner-filtered, ordered saved-workspace pages. All records undergo the existing `assertRecords` validation, including cross-page duplicate checks and tombstones. Only undeleted trade payloads reach the shared engine. Account filtering and latest-session (`today`), seven-date (`week`), or all-history scope use that same engine; all-account scope is supported. Missing cloud disclosure, a pending migration or invalid revision blocks dispatch. Browser-only/unsaved financial evidence cannot match the authoritative saved digest. The engine digest must match before reservation or OpenAI dispatch; workspace settings/revision are checked before/after snapshot loading and again after the provider result. A changed revision discards the answer. The client must still discard responses whose owner/account/range/data/request epoch changed in flight; the final server revision read cannot lock out a subsequent edit.

Limits are conservative refusal limits, not truncation: 250 rows/page, 101 page requests including the terminal empty page, 10,000 total saved records, 2 MiB per raw page and 8 MiB cumulative serialized page data. Settings responses are limited to 4 KiB. Short pages do not imply completeness; reading continues to an empty page. Each production storage request uses a 15-second timeout and cancels oversized response streams. Large otherwise-valid workspaces may receive `422 workspace_too_large`.

Success is exactly `{status:'ok',aiResponseUsed:true,contextDigest,selection:{choice_id,style}}`. No model prose is returned. The server validates the selection through `renderAskCovaSelection`; the client renders its own checked catalog. Failures return only safe status/error codes, never raw transport/provider errors or bodies. The shared route sets `Cache-Control: private, no-store`. This implementation adds no prompt, answer, trade, secret, or provider-response logging.

## Interaction and analytical question contract (v2)

The extra per-review AI consent flow has been removed, not automatically accepted. A deliberate starter activation or Send immediately begins one scoped request. Mounting, focusing, typing, selecting another account/date range, clearing, and timeouts never ask automatically. Retry is an explicit action. The three original starters remain; composer text is resolved locally and never enters the request. Provider/model branding and provider-specific errors are absent from the chatbot. This is not removal of whole-app Terms/privacy acceptance, sign-in, workspace-cloud disclosure, or the private-beta allowlist.

`AskCovaQuestion`, `ASK_COVA_QUESTION_IDS`, and `isAskCovaQuestion` are shared by the deterministic core and server, with the client importing the shared question type. Supported IDs are `review_results`, `explain_drawdown`, `what_stands_out`, `holding_time`, `setup_performance`, `time_of_day`, and `long_vs_short`. Missing planned risk is not a prerequisite for P&L, win-rate, profit-factor, or source-supported comparisons; unsupported evidence gets explicit limitations rather than invented values or an unrelated risk-only replacement review.

Setup labels and comparison metadata now participate in the local context digest so edits cannot reuse an old result. Validated setup labels may be displayed in local checked answers, but **never enter the provider payload**. Raw notes, composer text, account identity and trade IDs remain excluded. The selector sees actual checked numeric observations in separately constructed provider-safe variants, with setup categories named `Category A`/`Category B` by comparison rank rather than private labels. No string replacement/redaction is used. Both local wording and these safe variants bind the context digest; only local variants render after a checked selection. Specific questions lead with their comparison, mean gap, counts, currency/basis and coverage; extended selection methods and confounding remain in detail. Review summaries retain P&L, win rate and profit factor. The allowlisted payload remains bounded (at most three choices, 8,192 UTF-8 bytes); the whole provider request remains capped at 24,000 bytes. The response remains exactly a checked `{choice_id,style}` selection, with model, output-token cap, reservation and nonresetting cumulative-budget behavior unchanged.

`protocolVersion` is a wire compatibility field, not a consent attestation or authorization grant. Legacy `consentVersion`, extra fields, wrong/missing protocol, unknown question IDs, and raw duplicate/escaped-duplicate keys fail before storage/reservation/provider dispatch. Synchronous conversation epoch, selected exchange, in-flight controller, and live owner/session authority—not rendered button state—guard double activation, Clear/Send/retry races, retained actions and late results. Scope changes unmount and abort the old conversation. Local Show trades/Tell me more retain their exact checked reply; the complete conversation remains bounded to 20 exchanges.

## Explicit configuration prerequisites

A separately authorized operator must configure and verify:

- Existing `WORKSPACE_SYNC_ENABLED=true`, canonical `WORKSPACE_SYNC_PROJECT_REF` / `SUPABASE_URL` binding, and working policy-accepted auth and service storage.
- Server `ASK_COVA_ENABLED=true` (literal lowercase string) **and** server-only `ASK_COVA_BETA_USER_ID` containing the independently verified single-account UUID. Turning the server flag off, removing the UUID, or supplying invalid configuration closes discovery and dispatch. A frontend flag can never grant access; the UI must honor authenticated `ask_cova_access` discovery and its own explicit-action/authority checks.
- A server-only `OPENAI_API_KEY`. Do not use a `VITE_` credential. No key is created or provisioned by this patch.
- `ASK_COVA_BUDGET_ID`: an explicitly approved campaign identifier, 1–64 letters/digits/underscore/hyphen.
- `ASK_COVA_BUDGET_MICRO_USD`: an explicitly approved integer cap from 260,000 through 10,000,000 micro-USD. There is no default. The code maximum is $10 of reserved provider-token spend; this is not approval to spend $10.
- Existing Redis credential names **`KV_REST_API_URL` and `KV_REST_API_TOKEN`**, matching `api/_lib/rithmic-limit.js`, not guessed `UPSTASH_*` names. Only a canonical HTTPS `*.upstash.io` origin is accepted; credentials, ports, paths, queries and fragments in the URL are rejected. Redirects are refused. There is no local/in-memory production fallback.

The Redis database must provide atomic Lua and durable, non-evicting storage for budget/request receipts. Verify persistence, retention, backup/restore semantics, ACLs and provider behavior independently before enabling. All production instances must share the same approved database. Requests require an already initialized, nonexpiring budget hash with matching campaign/cap and valid cumulative usage. Missing or malformed state denies; the request path never initializes or repairs it. Initial provisioning is a separately reviewed, create-only operator action after establishing no prior allowance/spend and no residual namespace state. Never recreate a lost ledger as if it were new. A valid-looking stale restore can still roll back history: disable dispatch before any database switch, restore, or uncertain integrity, and do not resume without reconciling all prior charges. This is not a promise of rollback-proof storage.

## Durable reservation semantics

One atomic Lua script in the separate `ask-cova:{reservation-v1}:` namespace checks:

- Owner attempts: at most five per 60-second window.
- One in-flight call per owner, with a 300-second lock; normal completion releases only that matching lock.
- At most 20 accepted reservations per owner per UTC day, using Redis `TIME`, not a caller-supplied clock.
- Permanent idempotency by validated owner UUID plus request UUID (case-insensitive UUID identity).
- A global cumulative campaign budget, reserving **260,000 micro-USD ($0.26) before each provider attempt**. This is deliberately conservative reservation accounting, not the expected provider bill.

Budget/campaign metadata and accepted-request receipts have **no TTL**. No monthly reset exists. The campaign and cap must already be pinned in the single fixed budget key before requests are enabled. Changing either environment value is denied, not treated as a new budget. Missing campaign, cap or used fields, malformed usage, an expiring budget, and absent budget state are denied before reservation writes. Requests and locks do not use campaign-specific identities, so rotating a campaign string cannot reopen replay permission. Rejected requests do not consume the monetary reservation; requests with uncertain reservation or provider outcomes are never retried automatically. Accepted reservations are **never refunded**, even after a timeout, malformed result, context change or failed dispatch. An unlock is not a refund.

Any future campaign rotation/cap amendment is a separate manual financial authorization and reviewed maintenance procedure: stop dispatch, wait out in-flight work, preserve the cumulative ledger and replay receipts, audit prior charges and explicitly approve the next allowance. This patch intentionally supplies no reset or rotation endpoint. Never delete budget/receipt keys as a recovery shortcut.

No IP limit is claimed: this route has no verified, documented trusted-platform IP attestation. Do not trust caller-supplied `X-Forwarded-For` for financial enforcement. Owner limits plus the global cap apply; an edge/platform abuse rule can be added only after its trust boundary is verified.

## Provider and cost bound

Provider/model/endpoint are code-owned: `gpt-6-luna`, HTTPS `api.openai.com/v1/responses`, `reasoning.effort=none`, `store=false`, `service_tier=default`, `tools=[]`, `max_output_tokens=120`, and the prototype's explicit caching policy `prompt_cache_options:{mode:'explicit'}`. No arbitrary model or base URL environment override exists. The checked engine payload contains only allowlisted choices/wording, not identity, account IDs, trade IDs, raw trades, notes, setup text or rules. The entire serialized request—including instructions and strict JSON schema—is capped at 24,000 UTF-8 bytes before reservation.

Pricing and model limits were reverified against OpenAI's official documentation on October 31, 2026: maximum input 922,000 tokens; standard input $0.10/million, output $0.50/million, cache writes $0.125/million. Source: `https://developers.openai.com/api/docs/models/gpt-6-luna.md`. The preventive spending envelope no longer relies on estimating tokens from serialized bytes. Conservatively price the model's full admitted input maximum as cache writes, apply the documented long-context multipliers (2x input/cache, 1.5x output), the configured 120-token output maximum, and a further 10% regional premium: `(922000 / 1000000 * 0.125 * 2 + 120 / 1000000 * 0.50 * 1.5) * 1.10 = $0.253649`. Round upward to a $0.26 reservation. The existing explicit-cache payload has no breakpoints, but the envelope still allows the higher cache-write price. No token-count API call is added or assumed free. A $1 allowance therefore permits at most three accepted attempts, including failed/uncertain attempts, with no refund/reset. Existing byte and response-usage limits remain stricter validation gates, not the basis of this financial bound. No tools, images, web search or audio costs are permitted. This covers provider-token spend, not taxes, infrastructure, unrelated API calls, or provider pricing changes. Disable and reverify on model/pricing changes; do not silently continue at a changed rate.

Provider transport has a 15-second timeout, no retries, redirect refusal, a 64 KiB streamed response cap, fatal invalid-UTF-8 decoding, duplicate-key rejection and depth checks. It requires the exact model, default service tier, completed status, bounded integral usage, one completed assistant message and one output-text part without annotations. Tool/refusal/extra outputs, extra selection properties, invented choices/styles and malformed JSON are rejected. A malformed or unknown provider outcome retains its reservation. Returned usage is validation only; it never lowers a reservation.

`store=false`, non-training defaults and explicit caching are **not** a zero-retention promise. Review the official data controls and applicable account terms before publishing user disclosure: `https://developers.openai.com/api/docs/guides/your-data`. Do not claim Zero Data Retention without separately confirmed eligibility and configuration.

They cover owner/project/auth dispatch ordering, disabled/misconfigured operation, strict protocol/body validation, saved-digest parity, tombstones, account/date scope, torn snapshots, late revision changes, limits, provider envelope attacks, no-retry errors, checked success and no prompt leakage. No repository runtime generation is performed by the new scripts.

Budget transport tests cover configuration, exact atomic-command wiring, denials, malformed backend responses, cancellation, unknown outcomes and no retry/refund. **These injected-transport tests are not proof that Redis executed the Lua.** The budget script includes an actual Redis test for simultaneous near-cap reservations, same-owner concurrency, persistent replay rejection, campaign/cap pinning, unknown committed outcomes, attempts and daily limits. It starts its own isolated loopback Redis child, disables persistence, uses a scratch directory, and never connects to an existing or remote database.
