# Ask Cova: legacy v3 server rollout gate

The current v4 account-data implementation is documented in [ask-cova-account-data.md](./ask-cova-account-data.md). The contracts below describe the retained v3 path and its prior rollout. V4 adds the authenticated `ask_cova_context` read action, a generic query planner/executor, relevant saved notes and Passport data, and combined two-stage accounting; do not apply the v3 no-notes or one-generation statements to v4.

**Implementation is disabled by default. This document is not deployment, spending, credential-provisioning, or database-change authorization.** No paid calls, customer-data calls, credential reads, external configuration changes, or deployment were used for these regressions.

## Boundary and contract

Ask Cova uses POST actions on the existing `/api/workspace`, not a new function. The existing workspace-enabled/project-binding guard, policy-accepted authentication, UUID validation and exact owner comparison run before discovery or dispatch. A bounded routing-body parse selects authentication options; parse errors are deferred until after authentication. Only `ask_cova` and `ask_cova_access` POST actions call `requirePolicyAcceptedUser(req, {billing:false})`: verified Supabase identity and current-policy acceptance remain mandatory, without subscription resolution. Existing consent/apply/GET retain the original default billing authentication, including billing-derived workspace trade limits. Free and Pro use identical conservative Ask Cova limits; this adds no subscription gate.

### Single-account private beta

`server/askCovaAccess.ts` exports the shared `hasAskCovaAccess` gate used by both the workspace dispatcher and the actual Ask Cova handler. Access requires **both** literal server `ASK_COVA_ENABLED=true` and one valid, exactly 36-character UUID in server-only `ASK_COVA_BETA_USER_ID`, exactly matching the policy-verified authenticated `user.id`. There is no default, broad-enable fallback, list, wildcard, email rule, metadata rule or frontend configuration authority. Whitespace is not trimmed and identity is not guessed or normalized. The real approved account UUID must be independently verified and configured by a separately authorized operator; no account identity is hardcoded here. All regression account IDs are synthetic.

Missing/malformed configuration, a nonmember, or the kill switch returns generic HTTP 404 `{status:'unavailable',error:'ask_cova_unavailable'}` for `ask_cova`. Neither the configured UUID nor an invitation reason is disclosed. Authorization precedes workspace snapshot reads, budget configuration/reservation, Redis and provider calls, even when the actual handler is called directly. Direct handler callers must supply the already-verified auth user, never a user derived from request fields. The route retains `requirePolicyAcceptedUser` (Supabase `/auth/v1/user` verification plus current-policy acceptance), explicitly with `billing:false` for the two Ask Cova POST actions so even separately configured billing cannot contact billing Redis or Stripe before denial/discovery; no JWT body decoding or email-to-UUID guessing is introduced.

Capability discovery is **POST** `/api/workspace` with exactly `{action:'ask_cova_access',owner}`. After the existing project/auth/policy/same-owner checks, it returns exactly `{owner:user.id,enabled:boolean}` with `Cache-Control: private, no-store`. Nonmembers receive `enabled:false` for their own authenticated owner, never the invited identity. Extra fields and raw duplicate JSON properties are rejected. Discovery does not read a trading snapshot, check provider credentials, reserve budget, contact Redis, or dispatch a provider call. `enabled:true` means beta authorization only, not provider/budget readiness or spending permission. Pre-parsed bodies cannot reveal duplicates already discarded by the hosting platform. GET remains workspace snapshot loading, not a discovery alias. Existing GET/apply/consent remain available to nonmembers under their unchanged checks.

The legacy request has exactly `action`, `owner`, `account`, `range`, `question`, `contextDigest`, `protocolVersion`, and UUID `requestId`, with a 4 KiB serialized UTF-8 bound. Conversational requests add one optional `conversation` object containing the actual `message` and bounded `history`, with a 12 KiB outer request bound. Protocol remains exactly `ask-cova-v3`. Client trades, journal notes, metrics and provider configuration are not accepted. Deliberately typed Cova messages are now accepted as untrusted conversation, not financial authority. Duplicate properties are rejected when raw request text is available; when the hosting platform supplies a pre-parsed object, overwritten JSON properties are no longer observable. The surviving object still undergoes the exact field/value checks.

Server reads are owner-filtered, ordered saved-workspace pages. All records undergo the existing `assertRecords` validation, including cross-page duplicate checks and tombstones. Only undeleted trade payloads reach the shared engine. Account filtering and latest-session (`today`), seven-date (`week`), or all-history scope use that same engine; all-account scope is supported. Missing cloud disclosure, a pending migration or invalid revision blocks dispatch. Browser-only/unsaved financial evidence cannot match the authoritative saved digest. The engine digest must match before reservation or OpenAI dispatch; workspace settings/revision are checked before/after snapshot loading and again after the provider result. A changed revision discards the answer. The client must still discard responses whose owner/account/range/data/request epoch changed in flight; the final server revision read cannot lock out a subsequent edit.

Limits are conservative refusal limits, not truncation: 250 rows/page, 101 page requests including the terminal empty page, 10,000 total saved records, 2 MiB per raw page and 8 MiB cumulative serialized page data. Settings responses are limited to 4 KiB. Short pages do not imply completeness; reading continues to an empty page. Each production storage request uses a 15-second timeout and cancels oversized response streams. Large otherwise-valid workspaces may receive `422 workspace_too_large`.

Success is exactly `{status:'ok',aiResponseUsed:true,contextDigest,answer:{version:'ask-cova-answer-v1',paragraphs,detail}}`. Each paragraph is `{text,evidence}`: the model authors sentence flow with atomic `{{f:id}}` fact and `{{c:id}}` category placeholders. Server and client independently validate against their issued catalog using `renderAskCovaAnswer`. Private labels are resolved once locally as escaped React text, never returned by the server. Legacy selections fail closed; there is no canned answer fallback. Failures return only safe status/error codes. The shared route sets `Cache-Control: private, no-store`. No prompt, answer, trade, secret, or provider-response logging is added.

## Interaction and analytical question contract (v3)

The extra per-review AI consent flow has been removed, not automatically accepted. A deliberate starter activation or Send immediately begins one scoped request. Mounting, focusing, typing, selecting another account/date range, clearing, and timeouts never ask automatically. Retry is an explicit action. The three original starters remain. Actual starter/composer wording and recent successful Cova exchanges enter conversational requests; the finite intent resolver is only a fact-selection hint, not a gate that blocks ordinary follow-up messages. Provider/model branding and provider-specific errors remain absent from the chatbot. This is not removal of whole-app Terms/privacy acceptance, sign-in, workspace-cloud disclosure, or the private-beta allowlist.

Conversation context contains at most three complete prior user/assistant pairs, a current message of at most 500 characters, prior message contents of at most 4,800 characters, and at most 8,000 UTF-8 bytes for the complete conversation JSON. The UI builder drops oldest complete pairs when needed, never truncates the current question or retains half a pair. Server parsing rejects malformed/oversized context, extra keys and unsupported roles. The context binds the catalog digest and is included identically in count and generation. Only successful prior replies from the current scope are eligible; Clear, owner/session or account/range/data changes revoke old context. No provider-persisted conversation is created and `store:false` remains.

`AskCovaQuestion`, `ASK_COVA_QUESTION_IDS`, and `isAskCovaQuestion` are shared by the deterministic core and server, with the client importing the shared question type. Supported IDs are `review_results`, `explain_drawdown`, `what_stands_out`, `holding_time`, `setup_performance`, `time_of_day`, and `long_vs_short`. Missing planned risk is not a prerequisite for P&L, win-rate, profit-factor, or source-supported comparisons; unsupported evidence gets explicit limitations rather than invented values or an unrelated risk-only replacement review.

Setup labels and comparison metadata bind the `ask-cova-core-v2` digest. The `ask-cova-facts-v1` packet is an explicit allowlist of decimal facts, code-owned units/basis, distinct full/usable/sample/described coverage, typed observation predicates and required evidence IDs. The application does not automatically attach private setup names, journal notes, dates, account/owner IDs, trade IDs, digest or request IDs to provider input. Actual Cova messages are a separately authorized input: anything the user deliberately types in a message is part of that message. Private labels use neutral Category A/B descriptions; typed category nodes are resolved exactly once locally, never ordinary-word replacement. Prior assistant context uses validated main-answer text with safe category descriptions, not private-label UI text. Other category descriptions are source-owned direction, holding-span or clock buckets. Chat history is untrusted context; current server-verified facts remain the authority for financial claims.

The packet is limited to 24 facts, eight observations, three coverage records, two aliases and 8,192 UTF-8 bytes; the full provider request is capped at 24,000 bytes before reservation. Authored responses have one or two main paragraphs (maximum 160 rendered words), zero or one detail paragraph (maximum 80 words), no minimum-length padding, 32 atom occurrences, four evidence references per paragraph, 2,200 template characters per paragraph and 3,600 total. Unknown/malformed atoms, literal Unicode decimal digits/currency/percent symbols in prose, duplicate references, controls/bidi, markup/links, unknown keys, foreign prototypes, accessors and symbols are rejected. Every atom must belong to a cited observation, main paragraphs must cover required evidence, and detail may only elaborate main-answer evidence. Material subset/fee notices are derived from cited coverage in code.

### Consistent product personality

`server/askCovaPersonality.ts` owns the versioned `cova-personality-v2` identity and plain-trader-language guidance. The server prefixes it to the developer instructions on every admitted generation payload, independently of owner, question or conversation history. The same exact instructions enter the preflight token count. This is a shared product voice, not shared customer memory; authorization, private-beta scope and data isolation do not change.

Conversational catalogs do not force every reply to recap overall results, payoff and a comparison. The model receives the actual current message and recent chat, and selects relevant issued observations. A no-financial-facts conversation observation supports greetings or clarification without inventing metrics. Financial atoms still require their issued observation, applicable availability requirements remain, and material coverage/fee notices remain code-derived. Unsupported facts call for a plain limitation or clarification, not invented figures. This does not guarantee novel conclusions for unchanged data or prove real model relevance from a transport test.

At display time, issued USD money atoms use a leading dollar symbol after any negative sign. Decimal precision and provider fact values/displays remain unchanged. This is not global text replacement: literal USD in authored prose or private category names, and non-USD currency identities, remain intact.

The voice is lowercase, warm, direct and grounded, with a useful interpretation first rather than a metrics report. Instructions target two or three short sentences, usually 25–50 words and at most 60 words for the main answer; optional detail also targets at most 60 words. These are model instructions, not a new runtime word-limit guarantee: the existing 160/80-word structural safety ceilings remain unchanged. Do not convert an otherwise checked answer into a new paid failure merely for missing a style target. Tone examples are hypothetical style contrasts, not canned replies. Warmth is permitted; invented feelings, motives, causation and trade recommendations remain prohibited. Required evidence references do not require enumerating every fact in an observation.

The personality regression exercises fresh synthetic authorized owners/questions through the actual handler and asserts a stable versioned developer instruction plus count/generation parity and privacy. It proves consistent delivery, not that a real model follows the voice or that users like its output. Evaluate actual answers separately before claiming the wordiness or personality problem is resolved.

Structural validation is **not semantic entailment**. Valid references and exact atoms can still accompany reversed predicates, invented spelled-out quantities, wrong denominators, unsupported causality or forecasts. Synthetic fixtures verify the contract, not voice quality or truthfulness of actual model prose. Parent-only real-provider review remains required.

The Tell me more button reveals already-authored, validated detail from the same response, bound to its source exchange/reply/digest, without another request. Empty detail has no action. A typed follow-up is a new deliberate conversational request. Show trades derives scoped support from the union of cited observation IDs; provider-supplied trade IDs are never accepted. Comparison support includes the full universe needed for coverage, not a claim that every displayed row contributes to each mean. The client answer ceiling is 8 KiB; discovery remains 4 KiB, both with unique-key decoding and fatal UTF-8. Existing synchronous session-generation/owner/epoch/request checks remain.

Legacy catalog variants and the isolated selection renderer remain only as regression oracles and shared calculation/availability scaffolding. No live server/client/component path selects or displays them; they are never serialized to the provider. This deliberately avoids replacing the established financial and grouping oracles wholesale during the authored-protocol migration.

`protocolVersion` is a wire compatibility field, not a consent attestation or authorization grant. Legacy `consentVersion`, extra fields, wrong/missing protocol, unknown question IDs, and raw duplicate/escaped-duplicate keys fail before storage/reservation/provider dispatch. Synchronous conversation epoch, selected exchange, in-flight controller, and live owner/session authority—not rendered button state—guard double activation, Clear/Send/retry races, retained actions and late results. Scope changes unmount and abort the old conversation. Local Show trades/Tell me more retain their exact checked reply; the complete conversation remains bounded to 20 exchanges.

## Durable reservation semantics

One atomic Lua script in the separate `ask-cova:{reservation-v1}:` namespace checks:

- Owner attempts: at most five per 60-second window.
- One in-flight call per owner, with a 300-second lock; normal completion releases only that matching lock. The handler prepares the success/error response, awaits the existing cleanup in `finally`, and only then commits the HTTP response. This prevents response completion from preceding its cleanup attempt. A failed cleanup still preserves the answer/original error without refund or retry; it does not prove the lock was deleted. The existing expiry remains the fallback. A `request_in_progress` rejection indicates an uncleared lock, not a promise that the model is still generating; the client does not poll or retry automatically.
- At most 20 accepted reservations per owner per UTC day, using Redis `TIME`, not a caller-supplied clock.
- Permanent idempotency by validated owner UUID plus request UUID (case-insensitive UUID identity).
- A global cumulative campaign budget, reserving **4,000 micro-USD ($0.004) for each future admitted attempt, before the free token count and any paid generation**. This is conservative reservation accounting, not settlement or actual-cost billing.

Budget/campaign metadata and accepted-request receipts have **no TTL**. No monthly reset exists. The campaign and cap must already be pinned in the single fixed budget key before requests are enabled. Changing either environment value is denied, not treated as a new budget. Missing campaign, cap or used fields, malformed usage, an expiring budget, and absent budget state are denied before reservation writes. Requests and locks do not use campaign-specific identities, so rotating a campaign string cannot reopen replay permission. Requests denied admission do not consume the monetary reservation; requests with uncertain reservation or provider outcomes are never retried automatically. Accepted reservations are **never refunded**, even after a failed/unavailable/oversized token count, timeout, malformed result, context change or failed dispatch. An unlock is not a refund.

Any future campaign rotation/cap amendment is a separate manual financial authorization and reviewed maintenance procedure: stop dispatch, wait out in-flight work, preserve the cumulative ledger and replay receipts, audit prior charges and explicitly approve the next allowance. This patch intentionally supplies no reset or rotation endpoint. Never delete budget/receipt keys as a recovery shortcut.

No IP limit is claimed: this route has no verified, documented trusted-platform IP attestation. Do not trust caller-supplied `X-Forwarded-For` for financial enforcement. Owner limits plus the global cap apply; an edge/platform abuse rule can be added only after its trust boundary is verified.

### Prospective low-reservation correction (November 5, 2026)

Ordering is **authorization / request / saved-context / byte checks → existing atomic reservation → free official token count → paid generation → existing lock-only release**. Rate, daily, duplicate, in-flight and budget denials all precede any OpenAI transmission, including counting. The immutable serialized generation payload is built once; counting projects exactly `{model,input,reasoning,text,tools}` from that same string, preserving both messages and the complete structured-output schema. The original string is then sent unchanged for generation. No byte-to-token heuristic or count-failure fallback is permitted. Any future input-shaping fields require review of this projection and its parity tests.

Neither path generates, leaks provider details, refunds, or performs additional ledger operations. Both retain the admitted 4,000 charge and release only the lock through the existing `finally`.

Rates are ordinary input $0.10/million and output $0.50/million with the retained 10% contingency; explicit cache mode with no breakpoints/TTL overrides makes no cache writes. The 24,000-byte cap is still a separate payload-size guard, not a token proof. Default tier, reasoning none, no tools and 1,024 output tokens remain pinned. Disable and reverify on model/pricing/cache changes. The bound excludes taxes, infrastructure and unrelated API usage.
