# Ask Cova v4: read-only saved account queries

Implementation documentation, not deployment or spending authorization. Local synthetic test success does not establish live model schema acceptance, plan interpretation, semantic entailment or reply quality. The retained v3 request/catalog path is documented separately in `ask-cova-rollout.md`.

## Available data and explicit boundaries

V4 makes registered saved fields queryable rather than limiting natural questions to a finite topic enum. Sources: saved trade records, derived journal groups, daily journal notes, current workspace rules, account display names, historical Passport plans, saved Passport reviews, Passport reward allocations, and capability/availability metadata. Trade data includes saved dates/markets/direction/size/entry/exit/reported P&L/risk/setup/notes and explicit source timestamps where available. Notes and setup labels are authorized relevant inputs, but untrusted self-reported data, never instructions or computed financial truth.

This is not live unrestricted broker access. Opaque legacy cash, browser-only cash/freshness receipts/manual-net overlays, unsaved drafts, profile/avatar/billing/authentication secrets and other customers are excluded. Current balance/equity, open positions, per-trade allocated fees, missing execution fields and instrument taxonomy cannot be invented from P&L or saved market strings. A source inventory is not a claim that every inventoried field is available for every user. Recognizable secret-like text is withheld; pattern detection is not a guarantee of detecting every possible secret.

All actions retain verified policy identity, UUID and exact owner binding, project/workspace gates and server private-beta eligibility. Only `ask_cova`, `ask_cova_access`, and `ask_cova_context` use billing-free policy authentication; unrelated routes keep existing billing semantics. No new mutation endpoint, broker call, arbitrary SQL/code/URL execution, tool loop, provider override or scheduled/background data read is introduced.

## Complete data context

A deliberate Send/retry first POSTs `{action:'ask_cova_context',owner,account,range}`. The handler performs direct owner-filtered, bounded complete pagination of workspace records and Passport plan/review/reward tables. It does not call the capped Passport snapshot RPC as complete history, nor mutation-capable Passport inspect/review/plan RPCs. Workspace disclosure/pending-write/revision checks and separately hashed Passport rereads detect changes; they do not create a cross-table atomic transaction. Tombstones are not resurrected. Opaque cash is excluded from the returned snapshot.

Snapshot version `ask-cova-data-v1` has exact owner, workspaceRevision, workspaceRecords, passportPlans, passportReviews, passportRewards and complete-domain flags. The trusted loader must establish completeness; a caller-provided flag is not authorization. Shared validation checks nested plain descriptors, exact fields, IDs, owner binding, duplicate records, finite values and bounded depth/nodes/bytes. Arrays are bounded at 10,000 records per domain; serialized snapshot is bounded at 8,388,608 UTF-8 bytes. Oversized complete reads fail, never silently sample.

Snapshots at most 2,097,152 bytes retain the direct object response. Larger responses use `ask-cova-context-page-v1` with exact `{version,owner,snapshotHash,totalBytes,offset,nextOffset,encoding,chunk}`; encoding `base64`, decoded chunks at most 2MiB, at most four pages, final nextOffset null. Followups add a cursor containing exact version/owner/hash/totalBytes/offset. Each followup reauthorizes and rereads complete sources, rejecting drift. Cursor is not an access grant. Responses remain private/no-store and below the hosted 4.5MB payload ceiling. Browser checks contiguous offsets, canonical encoding, sizes, full SHA-256, fatal UTF-8, duplicate-free JSON and snapshot schema before any paid dispatch. No public object storage, uploads, persistence or automatic paging restart.

Browser authority combines live owner/session, workspace saved-state epoch/baseline/pending writes and owner-aggregate Passport mutation epoch/count. Passport plan/review/mutation-capable inspect revoke synchronously before auth/dispatch and release in finally; GET does not mutate this authority. Catch-up handles pre-mount/owner-change notifications. Scope changes, changed saved data and stale pending results revoke history/evidence. Cross-tab writes are detected through fresh server context/snapshot comparison, not an asserted global browser event guarantee.

## Scope, queries and proof

Default scope is the visible account and today/week/all selection. Date basis is recorded date; anchor is latest scoped saved trade/daily note/Passport review/reward date, with plans only when no account-dated evidence exists. No machine-clock 'today' substitution. Current rules are owner-global current configuration; Passport plans are separate owner-global historical saved limits. All-account daily notes require all-account selection. A model cannot widen account/date scope; a user must choose the broader visible scope and submit again.

The planner receives code-owned registry/capability/scope metadata and actual current/recent chat. It composes bounded `aggregate`, `rows`, `distinct`, `text_search`, or supported `sequence` operations. At most two queries, two group dimensions, four measures, bounded typed predicates and fixed result limits. No natural-language topic regex grants access. Runtime parsing remains mandatory despite strict provider JSON schema. Query semantics live in the shared registry and executor.

Full scoped scans precede top limits. Monetary aggregates retain compatible currencies/bases; monetary grouping, distinct and distinct counts preserve amount, currency, field-specific basis and unavailable reason. Unknown or incomplete money is not zero. Independent counts remain available where monetary fields are missing. Counts distinguish records/journal groups, never certify completed positions. Exact rational/minor-unit arithmetic, reliable timestamp/DST handling, full-match coverage, omissions and ties are exposed. Complete results beyond bounds ask for narrowing; top-k results explicitly remain top-k. Text search is literal, not full-corpus semantic classification. Selected text is supplied in a separate marked untrusted user-data message, never interpolated into developer policy.

`reported_drawdown` and `loss_streak` use strict sequence plans on trades, `order:'verified_close'`, complete mode, limit one. Existing v3 reliable chronology is reused: distinct valid dates establish day order; same-day records require distinct supported closing instants. Invalid/present mismatched closes fail; no ID tie-break. Drawdown begins at initial zero within matched records, not account balance/intratrade equity. Streak uses reported raw records; filtering exclusions are disclosed. Unsupported chronology/money/empty populations produce unavailable cells, never fabricated zero.

Generation POST exact v4 fields are action, protocolVersion, owner, requestId, snapshotDigest, contextDigest, account, range, conversation. No client fact arrays, query plans or provider settings are accepted as authority. Server rebuilds context and compares digests before reservation. Success returns exact status/aiResponseUsed/protocolVersion/requestId/snapshotDigest/contextDigest/plan/planDigest/resultDigest/answer. Client independently parses and executes the returned plan against its captured complete snapshot, recomputes digests and locally issues evidence/atoms. It does not trust provider-supplied facts or support IDs.

Answer v2 uses issued fact/category/quoted-text atoms and cited observations. Numeric claims cannot be supplied as unchecked literal numbers. Main text retains 160 rendered-word ceiling, detail 80, total rendered text 4,800 characters; detail only elaborates main-cited observations. Personality asks for substantially shorter, familiar trader language. Text inserts once as escaped React text, never HTML/Markdown or recursive tokens. USD money displays `$`/`−$`; other currency identities and literal saved text remain unchanged. Evidence actions use replayed snapshot support. Default replies show concise material qualifiers; local Answer details exposes every original scope/provenance notice without a provider request. Unknown notice templates remain visible rather than being silently hidden. Reference closure does not prove prose entails the facts or that a planner chose the right query.

## Two-stage provider and financial lifecycle

One unchanged 4,000 microUSD admission reservation covers the complete v4 attempt. No ledger/Lua/campaign/cap/history/reset/refund changes. Planner generation max output384; answer max output640; total configured output at most1,024. Planner exact input count C1 must be positive and at most8,192. Final exact count C2 must be positive and C1+C2 at most28,096. Each count projects immutable model/input/reasoning/schema/tools from that stage's exact generation JSON. At most two counts and two generations, sequentially; no repair/retry/fallback inference. Every admitted failure retains its charge and awaits bounded lock-only cleanup before response.

Both stages preserve existing code-owned model, default tier, reasoning none, store false, tools empty, explicit caching without breakpoints/TTL overrides. Under the verified ordinary input/output rates and no-cache-write behavior, the original combined bound including10% contingency remains3,653.76microUSD, rounded to4,000. Counts are summed, not deduplicated between stages. Documentation/pricing/API behavior changes require re-verification. Stage envelopes validate model/tier/completion/per-stage usage; byte ceilings are separate transport guards, not token estimates.

Context work is bounded at 24 seconds per page; generation work at 54 seconds plus at most 6 seconds lock-only cleanup, below the unchanged 300-second lock. For context/v4 routes only, each default identity/policy phase including body decoding is bounded at 5 seconds, with a 10-second enclosing pair. V4 session resolution is bounded at 5 seconds. The client deadline is derived as `4*(5+10+24) + (5+10+54+6) + 24 = 255 seconds`, including separate 12-second local preparation/completion allowances. After context validation, paid dispatch requires more than 87 seconds remaining. Authority capture has a separate watchdog; after capture, UI and client share the same absolute deadline. This is not a 255-second bound on the entire Send/capture interaction. Monotonic elapsed checks and abort races deny late dispatch. Local allowances are budgets, not promises about arbitrary network or scheduling delays. No timeout automatically retries or refunds; cancellation cannot prove provider work/billing stopped.
